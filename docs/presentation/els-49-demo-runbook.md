# ELS-49 — Local demo and individual rehearsal

This is an operator script, not evidence of a team rehearsal. Use only a **fresh task-owned** `els-demo-*` Compose project and the synthetic ELS-45 fixtures. Run from the reviewed checkout with Java 17, Docker Desktop, and a private existing `.env`; never print `.env`, the demo context, Authorization headers, passwords or full container environment. The current package is a staff-managed backend API, with no UI/student portal. [Delivery runbook](../deployment/local-setup.md) owns detailed packaging/reset semantics; this document does not replace it.

## Setup, backup decision and deterministic scenario

1. Record `git rev-parse HEAD`, `git status --short`, JAR SHA-256 after build, selected project/port and the terminal outcome in [ELS-49 evidence](../../reports/sprint-4/els-49-presentation-rehearsal.md). Check `docker compose -p els-demo-els49 --env-file .env ps -a` and `docker volume ls --filter label=com.docker.compose.project=els-demo-els49` before using the name. If either has resources you do not own, **stop** and choose another fresh name. An existing checkpoint under `target/els45-<project>.json` means stop and inspect; never discard it to make a pass.
2. Back up anything that matters before using a disposable project. The demonstrated fixture database is **not** a backup of user data. For a disposable rehearsal, record the reviewed source and checkpoint path; retain source-scoped ELS-47 evidence as the offline presentation backup. Do not run `down -v`, reset or reseed a non-disposable database. If the intended project is not empty/owned, stop instead of overwriting it.
3. Set private, distinct database and staff values in the existing ignored `.env` without echoing them. Never overwrite that file. From the same PowerShell shell, run `./mvnw.cmd --batch-mode --no-transfer-progress verify`; if required, start the isolated `els-tests` database, import its configuration using `tools/demo/import-test-environment.ps1`, run `./mvnw.cmd --batch-mode --no-transfer-progress -Pdatabase-test verify`, then stop only `els-tests` as in the delivery runbook.
4. With an unused loopback port (default 8080), run `docker compose -p els-demo-els49 --env-file .env up --build -d --wait`; check native exit status. Run `./tools/demo/wait-for-health.ps1 -BaseUrl http://127.0.0.1:8080` and then `./tools/demo/els49-rehearsal.ps1 -ProjectName els-demo-els49 -EnvFile .env -BaseUrl http://127.0.0.1:8080`. The rehearsal script uses the existing guarded seed and asserts public health, missing/wrong 401, authorized student/equipment/loan queries, active/returned history, duplicate-email 409 with unchanged counts, and the read-only seed rerun. It prints only assertion totals and generic outcomes; it does not create a second account, change business rules or auto-reset.
5. To demonstrate reset **only after checking that this is your disposable project**, use `./tools/demo/reset-demo.ps1 -ProjectName els-demo-els49 -EnvFile .env -ConfirmReset`. This invokes guarded Compose `down -v` and removes only its own checkpoint after successful Docker exit. Restart only that project, wait for health and rerun the rehearsal script; record the two distinct results. End with `docker compose -p els-demo-els49 --env-file .env down` (without `-v` if retaining the fresh disposable database). If you choose to remove its volume, use the same confirmed guarded reset, never a broad prune/down. Stop only task-owned `els-tests` if started.

The fixtures are fixed in identity/fields, while generated IDs and Beirut-local business dates are read from the guarded checkpoint. Rerun is an exact-state, no-write assertion. An interrupted or drifted checkpoint fails closed; investigate before explicitly resetting a disposable project. Health is public aggregate `{"status":"UP"}`; all eleven business operations require staff Basic access. [Staff boundary](../deployment/staff-access.md).
